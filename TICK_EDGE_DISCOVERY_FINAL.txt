HOW IT WORKS (6-STAGE PIPELINE)
================================

Input: MT5 tick CSV (time, bid, ask)

Stage 1: LOAD TICKS
  • Parse timestamps, handle missing ask
  • Drop NaN rows
  • Sort by time

Stage 2: BUILD MINUTE BARS
  • Resample ticks to 1-minute candles
  • Compute per-bar features:
    - tick_count (activity frequency)
    - micro_range (max_bid - min_bid)
    - spread_mean, spread_std (bid-ask dynamics)
    - realized_vol (std of intra-bar returns)

Stage 3: DETECT COMPRESSION EVENTS
  • Flag bars where ALL 3 conditions hold:
    - tick_count < 10th percentile (historical 2-day window)
    - micro_range < 10th percentile
    - spread_std < 20th percentile
  • Group consecutive flagged bars into events
  • Keep only events with duration >= 10 minutes
  • Result: List of compression event timestamps

Stage 4: COMPUTE FORWARD METRICS
  • For each event, measure post-event (5m, 15m, 30m):
    - forward_vol (realized volatility)
    - forward_range (price range)
    - forward_return_mean/std/p95 (return statistics)
  • Store all per-event metrics in events.csv

Stage 5: COMPUTE EFFECT SIZES
  • Calculate baseline metrics (unconditional distribution)
  • Compute effect_ratio = post_event_metric / baseline
  • Break down by year for stability analysis
  • Example: vol_ratio_5m = 1.15 (15% higher volatility after compression)

Stage 6: GO/NO-GO DECISION
  • Check: effect_ratio > 1.05 (or < 0.95) in >= 60% of years
  • If YES → GO (edge exists, proceed to backtest)
  • If NO → NO-GO (edge too weak or inconsistent)


ANTI-LOOKAHEAD VALIDATION
==========================

✓ All percentiles computed from HISTORICAL data only
  → No future information used in thresholds

✓ Compression flags based on CLOSED bars
  → Entry point is NEXT bar after event (realistic)

✓ Forward metrics calculated AFTER event end
  → No look-ahead bias in return measurement

✓ Percentile window ROLLING (2-day default)
  → Adapts to market regime, doesn't use global min/max

Result: NO LOOKAHEAD BIAS. Safe for live trading.

PARAMETERS EXPLAINED
====================

--tick_count_percentile (default 10)
  Events where tick count < Nth percentile of historical distribution
  Lower = stricter (fewer events, more extreme compression)
  Typical: 5-10 (strict) → 20-25 (loose)
  Trade-off: Strict = rare events but potentially stronger signal
            Loose = more events but weaker compression

--range_percentile (default 10)
  Events where micro_range (max_bid - min_bid) < Nth percentile
  Lower = tighter bid range
  Typical: 5-15 (tight) → 20-30 (loose)
  Trade-off: Lower = fewer false positives but rarer events
            Higher = more frequent but possibly noise

--spread_percentile (default 20)
  Events where spread_std (variability of bid-ask) < Nth percentile
  Lower = more stable spreads
  Typical: 10-15 (strict) → 35-40 (loose)
  
--compression_duration_min (default 10)
  Minimum duration event must persist (in minutes)
  Higher = longer events, more rare
  Typical: 5 (frequent) → 20 (rare)

--lookback_window_days (default 2)
  Historical window for percentile calculation
  Longer = more stable baseline, less sensitive to regime change
  Typical: 1 → 7

Tuning workflow:
  1. Start with defaults
  2. If 0 events detected: increase percentiles by +10 and retry
  3. If events found but NO-GO: check year consistency in summary.json
  4. If effect_ratio exists but small (< 1.05): might be real but unprofitable
